# GitLab Kubernetes build-container consumption

The existing released `gha-runner` image family supplies the **build container**.
It does not implement the GitLab Runner manager or helper protocol. Those two images
remain GitLab-owned, must match the same verified Runner release and target architecture,
and must also be promoted to approved Nexus paths by immutable digest.

Generate a credential-free configuration with Python 3.11 or later:

```sh
python3 scripts/gitlab_build_config.py publication-contract.json > config.template.toml
python3 tests/gitlab_build_config_test.py
bash tests/gitlab_build_image_test.sh ghcr.io/verjson/gha-runner@sha256:<verified-digest>
```

The contract is a JSON object with exactly these fields:

| Field | Required value |
| --- | --- |
| `registry` | Approved Nexus Docker hostname, optionally including its port |
| `namespace` | Dedicated Kubernetes job namespace |
| `architecture` | `amd64` or `arm64` |
| `build` | `{ "source": "ghcr.io/verjson/gha-runner[-variant]@sha256:…", "destination": "<registry>/<path>@sha256:…", "version": "<released SemVer>" }` |
| `manager` | Same record shape; source repository `registry.gitlab.com/gitlab-org/gitlab-runner` |
| `helper` | Same record shape; source repository `registry.gitlab.com/gitlab-org/gitlab-runner/gitlab-runner-helper` |

Ellipses above are documentation, not usable digests. Obtain complete references from
verified publication receipts. Each promotion must preserve its source digest. Resolve
the selected platform from the index and verify child/config digests, declared runtime
architecture, release identity, signatures, SBOM/license bindings and helper version
before deployment. **The renderer validates structure and consistency, not authenticity**:
caller-provided version labels or identical digests do not prove who published an image.
The manager reference appears in a comment for the deployment owner; it is not a build
image or a Kubernetes deployment generated by this script.

## Execution and isolation

GitLab's Kubernetes executor must bypass `/entrypoint.sh`. The template explicitly sets
`FF_KUBERNETES_HONOR_ENTRYPOINT=false`, uses the attach execution strategy and Bash.
The original image entrypoint remains unchanged for GitHub consumers. No GitHub token,
runner registration, Docker socket or host work directory belongs in the GitLab job pod.

The generated template runs one job at a time, pins the only allowed build image,
restricts pulls to `always`, drops all Linux capabilities, disables privilege escalation,
and runs UID/GID 1001 (observed in released base 0.2.1; revalidate each selected variant) with group-writable ephemeral volumes. The image's passwordless
sudo is consequently unavailable. Build and helper CPU, memory and ephemeral storage
have finite limits. Namespace/account/bearer overrides and job service-account token
mounting are disabled. Services use a nonmatching reserved `.invalid` image allowlist:
an empty allowlist would allow arbitrary services. Jobs needing service containers are
outside this initial contract and require separately reviewed digest-pinned allowances.

The deployment owner must add GitLab URL and the approved runner authentication secret
through its secret-management path, configure separate least-privilege manager RBAC,
and provide short-lived Nexus pull credentials. Do not put secrets in the JSON contract,
repository or generated template. The template neither registers a runner nor creates
credentials; it does not authorize a long-lived PAT publication fallback.

Apply namespace ResourceQuota/LimitRange, restricted pod admission, and network policies
before accepting jobs on the shared GitLab/Nexus host. Admission must prevent privileged
pods, host mounts/namespaces and feature-flag or pod-spec overrides from weakening this
profile. Same-host resource limits are not kernel isolation. Keep the initial canary
restricted to the approved project; untrusted multi-tenant jobs need a separate threat
assessment. Do not merge this template into an existing permissive runner configuration:
review the effective configuration and observed pod specification after registration.

## Acceptance receipts required before rollout

1. Preserve source release manifest, source/index/platform digests and source evidence;
   promote through the canonical explicit dispatch path, without rebuilding consumer images.
2. Pull from Nexus by digest with TLS verification. Record source/destination byte equality
   and the manager/helper binary versions and architectures. Account for registry support
   for OCI evidence/referrers; never silently drop provenance during promotion.
3. Run a real GitLab Kubernetes job that clones a repository, invokes Bash as UID 1001,
   uploads an artifact, and records the admitted pod's resource/security/image settings.
   Confirm no GitHub runner registration or listener process starts.
4. Exercise wrong-scope and expired credentials, attempted privilege/image overrides,
   resource exhaustion containment, and cleanup/rollback before organization adoption.

The structural unit tests are not these live deployment receipts. Track live acceptance
in [runner #198](https://github.com/Verjson/verjson-github-runner/issues/198) and
[CI #30](https://github.com/Verjson/verjson-ci/issues/30).
