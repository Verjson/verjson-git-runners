The four AI callers had drifted onto two different contract commits — the
privileged-merge pair on `6462e0cc` and the review pair on `55576f7c` — while
this repository's changelog and release callers sat on a third. That is the
unit-of-adoption problem in miniature: nothing constrains a repository to one
contract at a time, so each generated file rots on its own schedule and "which
contract is this repo on" has no answer. All four are now regenerated together
at `aecfb932`.

The regeneration is not cosmetic. At this contract the merge App's private key
is no longer a caller-passed `secrets:` input: the callee mints its token inside
a caller-owned deployment environment, so the caller declares
`merge_environment: merge-app` and `secrets: inherit` instead of
`MERGE_APP_PRIVATE_KEY`. The callee declares no `workflow_call` secrets, which
makes inheritance the only path by which the org-level key can reach it.

**This repository has no `merge-app` environment.** It has `production` and
`release-app`. Until `merge-app` exists with the deployment-branch policy the
canonical `app-key-environment` job asserts — `protected_branches: false`,
`custom_branch_policies: true`, exactly one policy named `main` — privileged
merge will fail closed on that assertion. Creating it is repository security
configuration that gates pushes to a protected branch, so it is deliberately
left as an explicit human step rather than performed as part of a pin bump.

The required-check descriptors passed to the generator were derived from this
repository's own ruleset and workflow list through the API, not read out of the
previous generated file's header. A generated header is human traceability; an
adopter-controlled string is not an input to a privileged invocation.
