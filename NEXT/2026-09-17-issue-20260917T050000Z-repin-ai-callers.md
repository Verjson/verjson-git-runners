title: Repin the four AI callers to one current contract SHA
impact: patch
---

The four AI callers had drifted onto two different contract commits — the
privileged-merge pair on `6462e0cc` and the review pair on `55576f7c` — while
this repository's changelog and release callers sat on a third. That is the
unit-of-adoption problem in miniature: nothing constrains a repository to one
contract at a time, so each generated file rots on its own schedule and "which
contract is this repo on" has no answer. All four are now regenerated together
at `aecfb932`.

The regeneration is not cosmetic. At this contract the merge App's private key
is no longer a caller-passed `secrets:` input: the callee mints its token inside
a caller-owned deployment environment, so the caller declares
`merge_environment: merge-app` and `secrets: inherit` instead of
`MERGE_APP_PRIVATE_KEY`. The callee declares no `workflow_call` secrets at all,
so there is no named grant left to make: the callee resolves the key from the
environment its job binds.

**Three environments back this change, and two of them did not exist when it
was written.** The regenerated callers name `merge-app` for privileged merge and
`ai-review-app` for the AI review pair; this repository had only `production`
and `release-app`. Both were created to the shape the canonical
`app-key-environment` job asserts — `protected_branches: false`,
`custom_branch_policies: true`, exactly one deployment-branch policy named
`main` — and verified by running that job's own jq against the live API.

Naming an environment that does not exist is not inert. GitHub creates a
referenced environment implicitly, with no branch policy at all, which quietly
converts a main-only confinement into no confinement. Creating them explicitly,
to the asserted shape, is what keeps that from happening on the first run.

The required-check descriptors passed to the generator were derived from this
repository's own ruleset and workflow list through the API, not read out of the
previous generated file's header. A generated header is human traceability; an
adopter-controlled string is not an input to a privileged invocation.

Repinning the callers alone left `tests/ai_review_caller_test.py` asserting the
old SHA through a single `CONTRACT` constant, so the required `shell-tests`
context went red. That constant was the deeper problem: this repository is on
**three** contracts at once — AI callers at `aecfb932`, generated artifacts at
`55576f7c`, container workflows at `3b83ddea` — and one constant cannot describe
that. It happened to spell the generated-artifacts SHA, so it was quietly
asserting the wrong contract for the AI callers even before this change.

The constant is now three named constants, one per family, and a new test walks
every `Verjson/.github` caller in `.github/workflows/` and requires its pin to
match its declared family, with no unregistered callee and no declared callee
that nothing invokes. Verified by mutation: pointing `ai-review-merge.yml` at a
stranger SHA fails two tests; reverting restores green.

The `merge-app` deployment environment this change needs now exists, created
with `protected_branches: false`, `custom_branch_policies: true`, and exactly
one `main` branch policy — the shape the canonical `app-key-environment` job
asserts, mirroring the `release-app` environment already in this repository.
That implements [ADR 0166](https://github.com/Verjson/.github/tree/main/docs/decisions/0166-environment-only-app-private-keys)
and [ADR 0180](https://github.com/Verjson/.github/tree/main/docs/decisions/0180-no-approved-organization-custody-for-environment-only-app-keys);
it decides nothing new.

Three contracts in one repository, and a test that could not say so, is the
concrete local shape of the root cause recorded in
[ADR 0185](https://github.com/Verjson/.github/tree/main/docs/decisions/0185-org-contract-distribution).

Regenerating the two privileged-merge callers at the current contract also moved merge
App key custody into the callee: the canonical generator now emits `secrets: inherit`
with `merge_environment: merge-app` instead of an explicit `MERGE_APP_PRIVATE_KEY`
grant, because under ADR 0166/0180 the key is an environment secret of `merge-app` and
is not in scope where the caller job runs — a caller literally cannot name it. Both
regenerated files were verified byte-identical to `scripts/gen-privileged-merge-caller.sh`
run at the pinned SHA, so nothing here is hand-written.

`tests/privileged_merge_caller_contract_test.sh` asserted the superseded shape and so
failed closed, which is the behavior that test exists for. It now pins the new digests
and asserts the environment binding that replaced the explicit grant, plus that
`MERGE_APP_PRIVATE_KEY` appears nowhere in either caller. Both new assertions were
mutation-checked: pointing `merge_environment` at `release-app` fails, clean passes.

The contract SHAs themselves moved into `tests/contract_pins.json`, read by both this
test and `tests/ai_review_caller_test.py`. Two tests keeping private copies of the same
pin is how this repository asserted the wrong contract in the first place.


One consequence is worth stating plainly, because it removes a control rather
than moving it: with `secrets: inherit` the caller names no secret, so nothing
in the caller's text bounds what it hands the callee, and the assertion that
`ORG_ADMIN_TOKEN` does not appear in the file no longer means anything it used
to. Byte identity is what replaces it. All four generated privileged callers —
the merge pair and the AI review pair — are now pinned by sha256, so a change to
any of them has to be a deliberate regeneration with a repinned digest.
